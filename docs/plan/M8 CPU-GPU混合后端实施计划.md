# M8 CPU-GPU 混合后端实施计划

## 前置条件

- M5 OpenMP 已完成正确性、线程数控制和 Release 性能实验；
- M6 CUDA 与 M7 当前回归保持全绿；
- Sequential、OpenMP 和 CUDA 的纯后端基线已经固定；
- 用户确认 M8 可以新增 `--hybrid-cpu-shares`，并将 CSV Schema 从27列向后兼容扩展为28列。

M8 不在 M5 完成前进入代码实施，避免以未稳定的 CPU 后端构建混合调度。

## 阶段一：共享契约与实验矩阵

1. 为后端模型增加 `Hybrid`，注册 `make_hybrid_executor()`；
2. 为请求和 `ExperimentSpec` 增加 CPU 工作比例；
3. CLI 接受 `--hybrid-cpu-shares`，仅在选择 Hybrid 时展开；
4. Hybrid 配置同时携带线程数、CUDA 批大小和 CPU 比例；
5. CSV 追加 `hybrid_cpu_share`，M1 兼容旧27列和新28列；
6. 输出目录标签包含三项配置，避免不同实验互相覆盖。

验收：矩阵数量、去重、稳定顺序、非法比例、单张图片 Hybrid 拒绝和旧 CSV 兼容测试通过。

## 阶段二：确定性任务划分

1. 新增 Hybrid 分区模型，保存 CPU/GPU 原始索引；
2. 实现均匀交错的静态比例分配；
3. 覆盖图片数为2、3、小于100、不能整除和极端比例；图片数1明确拒绝；
4. 实现按原始索引合并输出；
5. 检查丢失、重复、越界和来源路径错序。

验收：比例误差不超过一张图片，所有输入索引恰好出现一次，合并顺序稳定。

## 阶段三：OpenMP 与 CUDA 并发执行

1. Hybrid Executor 完成公共预检后启动 CPU/GPU 两个分支；
2. CPU 分支调用 M5 Processor，GPU 分支调用 M6 Processor；
3. 使用 C++17 明确异步执行策略，禁止实现退化为延迟执行；
4. 分支结果、异常和计时分别保存，汇合点统一判断成功；
5. 任一分支失败时清空本次输出和指标；
6. CUDA 显存回退成功时记录实际批大小。

验收：通过可控屏障测试证明两个分支重叠；Thread Sanitizer 可用平台下无数据竞争，Windows 下使用同步测试和代码审查补充。

## 阶段四：进度、计时与报告

1. 增加线程安全进度协调器；
2. 分别上报 `Hybrid CPU`、`Hybrid GPU` 和 `Hybrid overall`；
3. M7 使用完整 Hybrid wall-clock 生成 `compute_ms`；
4. CUDA 三段时间只汇总 GPU 子集；
5. Hybrid `parallel_efficiency` 保持为空；
6. 验证失败、分支失败或回退失败不生成伪造性能指标。

验收：计时结束后生成的轨迹单调且最终达到图片总数，被测区间无进度日志输出，CSV 语义与设计一致。

## 阶段五：M1 仪表板

1. 增加 Hybrid 后端和 CPU 比例输入；
2. 实验矩阵摘要展示线程数、批大小和 CPU 比例；
3. 结果图加入 Hybrid 配置；
4. 完成后静态轨迹提供完整视图和并行后端放大视图；
5. 历史27列 CSV 可读取；首次写入新结果时由 M7 原子升级并补空 `hybrid_cpu_share`；
6. 新28列 CSV 支持筛选、下载和运行上下文展示。

验收：Demo、旧历史、纯后端和 Hybrid 新结果均可读取；线条贴近时可在放大视图中分辨。

## 阶段六：测试与性能实验

### 自动化

- 分区：图片数 2、3、10、100，CPU 比例 1、10、25、50、75、99；图片数1验证拒绝；
- 正确性：黑白、渐变、不同分辨率、奇数裁剪和水印边界；
- 并发：两个分支确实重叠、内存进度协调线程安全、异常传播；
- 故障：OpenMP 不可用、CUDA 无设备、首次显存失败后回退、二次失败；
- 报告：28列 Schema、旧27列读取与原子升级、实际批大小和 CPU 比例；
- UI：Hybrid 矩阵、完成后轨迹三线、并行放大视图和历史兼容。

### Release 调参

采用分阶段实验，避免线程数×批大小×比例全部笛卡尔积造成测试爆炸：

1. 对三种图片规模测量纯 OpenMP 与纯 CUDA；
2. 固定各自较优线程数和批大小，粗测 CPU 比例 `10,25,50`；
3. 围绕最佳粗测比例进行 `±5` 或 `±10` 的细调；
4. 每组预热2次、正式5次，报告中位数和波动；
5. 记录功耗模式、温度、CPU、GPU、内存、Toolkit、驱动和实际批大小。

## 关闭条件

- M5、M6、M7、M8 和仪表板全部自动化测试通过；
- Hybrid 输出整批逐像素验证通过；
- 证明 CPU/GPU 分支并发而非串行；
- 旧27列和新28列 CSV 均可被 M1 读取；
- 至少三种图片规模完成纯 OpenMP、纯 CUDA 和 Hybrid 对比；
- 若 Hybrid 没有快于纯 CUDA，文档明确记录瓶颈，不以调换口径制造提升；
- 最终执行 CTest、`pytest -q`、真实 CLI 烟测和 `git diff --check`；
- 不留下构建警告、控制台异常或未记录的临时性能文件。

## 风险

- CPU 与 GPU 可能争用内存带宽，使 Hybrid 慢于纯 CUDA；
- OpenMP 线程可能挤占编排、解码或 GPU 驱动线程；
- 图片数量过少时任务划分和同步开销占主导；
- 静态比例可能因输入差异造成一个分支提前空闲；
- 轨迹日志必须在计时结束后统一输出，禁止在被测区间触发 stdout 或页面重绘。
