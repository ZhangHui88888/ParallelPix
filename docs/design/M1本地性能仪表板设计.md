# M1 本地性能仪表板设计

## 目标与边界

M1 是仅在本机运行的英文 Streamlit 单页控制台。它负责收集 Benchmark 配置、调用 M2 CLI、展示进程日志，并只读展示 M7 写入的 CSV。

M1 不读取或处理原始图片，不计算吞吐量、加速比或并行效率，不修改真实 Benchmark CSV，也不承担后台任务队列、远程访问和多用户并发。

## 页面结构

- 侧栏：运行模式、CLI 与数据路径、后端矩阵、图片数量、OpenMP 线程数、CUDA 批大小、测量模式和轨迹模式。重复计划由测量模式固定，不单独开放输入。
- 状态区：展示 `idle`、`validating`、`running`、`success`、`partial` 或 `failed`，最多保留 500 行日志。
- 指标区：直接选择 CSV 已提供的最佳加速比、峰值吞吐量、最快计算时间，并显示通过验证的配置数量。
- 结果区：包含 `Overview`、`Scalability`、`CUDA Timing` 和 `Raw Data` 四个标签页。
- 历史区：按 `run_id` 和 UTC 时间选择运行记录，默认显示最新一次。

Demo 模式始终显示“Demo data — not measured”，只读取仓库内的虚构样例数据，不启动 CLI。

## 运行流程

```text
用户配置
  → M1 基础表单校验
  → DemoRunner 或 SubprocessRunner
  → 退出码与日志
  → 只读加载 CSV
  → Schema 校验
  → 按 run_id 展示有效结果
```

- 选择 OpenMP 或 CUDA 时，M1 自动将 Sequential 加入请求作为基线。
- Subprocess Runner 使用参数数组和 `shell=False`，不接受整段 Shell 命令。
- CLI 退出码 `0` 为成功，`2` 为部分成功，其他值为失败。
- 成功或部分成功后必须存在结果 CSV，并出现新的 `run_id`，否则本次运行按失败处理。
- `validation_passed=false` 的行保留在原始表格中，但不进入性能图表。

## M2 命令契约

```text
parallelpix benchmark
  --input <dir> --output <dir> --watermark <file>
  --backends sequential,openmp,cuda
  --image-counts 10,50,100
  --threads 1,2,4,8
  --cuda-batches 1,4,8
  --warmups 2 --repetitions 5
  --csv <file> --append
```

图片数量、OpenMP 线程数和 CUDA 批大小均使用可自由输入的逗号分隔正整数列表；默认值分别为 `10,50,100`、`1,2,4,8` 和 `1,4,8`。输入会去重并保持首次出现的顺序，允许使用 `1` 进行 M4 Sequential 冒烟测试。

## CLI 调用与单次冷启动

M1 在启动 `parallelpix.exe` 前使用外部高精度时钟开始计时，并在子进程退出后停止。“完整 CLI 调用耗时”包含进程创建、动态库与后端初始化、完整 Benchmark 调用、CSV 写入和进程退出。它以 `<results>.lifecycle.csv` 侧车文件按 `run_id` 持久化，不修改 M7 的 27 列结果 CSV 契约。

多配置的一次调用只有一次进程启动，因此该运行级指标不可分摊给每一行配置。选择“单次冷启动基准”后，M1 启动一个全新 CLI 进程，关闭预热，并让所选矩阵中的每个配置运行一次；不再为每个 CUDA 配置额外启动探测进程，也不会重复执行 Sequential 基线。历史 `<results>.cold-start.csv` 仍可只读加载，但新运行不再生成该逐配置侧车文件。

稳态基准固定对每个配置执行2次预热和5次正式测量。处理轨迹只记录每个配置第1次正式样本，后续4次仍会执行并进入中位数、最小值、最大值和标准差，但不重复记录轨迹。界面不再提供可调重复次数，避免不同后端或不同运行使用不可比的样本数。

## 完成后处理轨迹

Local CLI 不提供实时轨迹开关，也不在 Benchmark 运行中重绘 Plotly。后端在内存中缓冲第1次正式样本的批次进度；Runner 在 `compute_ms` 与 `end_to_end_ms` 均停止计时后才输出轨迹日志。M1 捕获这些机器可读日志但不把它们写入运行中控制台，子进程结束后将样本保存到 `<results>.trajectory.jsonl`，并在 Overview 中绘制静态“处理轨迹”。

轨迹采样本身只进行内存计数与计时，不触发 stdout flush、Python 页面重绘或人为延迟。运行中普通文本日志最多每 200 ms 重绘一次。公开 CLI 参数、27列 CSV 和 CUDA Event 分阶段计时均不改变。

单次冷启动请求必须携带 `--cold-start`，并使用 `warmups=0`、`repetitions=1`；否则 CLI 会按稳态规则拒绝请求。

## CSV 契约

每行表示一个已经由 M7 聚合的实验配置。`compute_ms` 和 `end_to_end_ms` 为中位数；不适用字段保持为空。

```text
run_id, recorded_at_utc, backend, thread_count, cuda_batch_size,
image_count, input_resolution, output_resolution, warmups, repetitions,
compute_ms, compute_min_ms, compute_max_ms, compute_stddev_ms,
end_to_end_ms, end_to_end_min_ms, end_to_end_max_ms, end_to_end_stddev_ms,
images_per_second, megapixels_per_second, speedup, parallel_efficiency,
validation_passed, max_pixel_error, h2d_ms, kernel_ms, d2h_ms
```

缺少必需字段、时间戳无效、验证字段无法解析或 CSV 为空时，M1 禁止绘图并显示具体错误。

M8 实施后，M1 同时接受旧27列 Schema 和追加 `hybrid_cpu_share` 的新28列 Schema。旧记录为该字段补空值；Hybrid 新记录必须提供 CPU 比例。完成后的静态轨迹计划增加 Hybrid CPU、Hybrid GPU 与总体进度，并提供隐藏 Sequential 后自动缩放 Y 轴的“并行后端放大视图”，用于分辨贴近的 OpenMP/CUDA/Hybrid 轨迹。

## 最终配置对比

- 最终对比的主性能指标为“单张处理耗时中位数（毫秒/张）”，计算方式为 `compute_ms / image_count`；它使用每次完整计算任务耗时的中位数，避免偶发系统抖动主导结论。
- “端到端总耗时”使用 `end_to_end_ms / 1000`，以秒展示。
- 吞吐量、加速比和最终对比图都以 CSV 中的中位数统计为准；M7 CSV 没有算术平均耗时字段，仪表板不得将中位数标为平均值。
